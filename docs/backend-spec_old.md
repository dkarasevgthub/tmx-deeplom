## 1. Границы работы

**Входит:** REST API, аутентификация и права, вся бизнес-логика склада (заказы,
отгрузка, приёмка, движение остатков), выдача штрихкодов и рендер этикеток,
журналы и аудит, миграции, тесты, развёртывание.

**Не входит:** интерфейс (десктопное приложение уже написано), работа с
оборудованием (её ведёт локальная служба устройств на рабочем месте), обмен с
1С (отдельный этап, но `code1c` в схеме предусмотрен).

Функционал определяется тем, что уже умеет приложение. Полный перечень
охваченных сценариев — раздел 12.

### Правила слоёв

- `api.py` знает про HTTP и не знает про SQLAlchemy.
- `service.py` содержит бизнес-правила и владеет транзакцией.
- `repository.py` обращается **только к таблицам своего сервиса**. Нужны чужие
  данные — вызов метода чужого сервиса, а не `JOIN` через границу.
- Зависимости направлены вниз: `catalog` и `inventory` не зовут никого.

## 3. Аутентификация

**Схема:** access-токен (JWT, 15 минут) + refresh-токен (30 дней, ротация при
каждом обновлении, отзыв при выходе). Пароли — argon2id.

```
POST /api/v1/auth/login     {login, password} → {access, refresh, user}
POST /api/v1/auth/refresh   {refresh}         → {access, refresh}
POST /api/v1/auth/logout    {refresh}         → 204
GET  /api/v1/auth/me                          → {user, permissions}
```

`login` — часть e-mail до `@` либо e-mail целиком. Неверная пара — `401` с кодом
`invalid_credentials`, без уточнения, что именно неверно. Заблокированный
пользователь (`status = blocked`) — `403` с кодом `user_blocked`.

Пять неудачных попыток подряд с одного адреса — задержка 30 секунд.

При успешном входе обновляется `user_account.last_login`.

## 4. Права

Матрица «роль × раздел», хранится в БД и редактируется через API. Разделы:
`orders`, `shipping`, `receiving`, `catalog`, `stock`, `users`.

Значения по умолчанию (совпадают с текущими в приложении):

| Раздел | manager | stockman | admin |
|---|---|---|---|
| orders | просмотр + изменение | просмотр | просмотр + изменение |
| shipping | просмотр | просмотр + изменение | просмотр + изменение |
| receiving | просмотр | просмотр + изменение | просмотр + изменение |
| catalog | просмотр + изменение | просмотр | просмотр + изменение |
| stock | просмотр | просмотр + изменение | просмотр + изменение |
| users | нет доступа | нет доступа | просмотр + изменение |

Проверка — зависимостью FastAPI на каждом эндпоинте:

```python
@router.post("/orders", dependencies=[Depends(requires("orders", "edit"))])
```

Нет прав на просмотр — `403` `forbidden`. Нет прав на изменение при чтении
разрешённом — тоже `403`, но только на изменяющих методах.

Редактировать матрицу прав может только `admin`. Пользователь не может изменить
собственную роль и не может себя заблокировать или удалить.

## 5. Сквозные механизмы

### 5.1 Версия и формат

Префикс `/api/v1`. Все ответы `application/json`, ошибки —
`application/problem+json` по RFC 9457:

```json
{
  "type": "https://prozapas/errors/insufficient_stock",
  "title": "Недостаточно остатка",
  "status": 409,
  "detail": "На складе «Склад №1» доступно 12 шт., требуется 20",
  "errors": [{"field": "positions.0.qty", "message": "Доступно 12"}]
}
```

Коды ошибок домена: `validation_error`, `not_found`, `forbidden`,
`invalid_credentials`, `user_blocked`, `conflict`, `stale_version`,
`invalid_transition`, `insufficient_stock`, `barcode_not_found`,
`barcode_duplicate`, `already_completed`, `printer_required`.

### 5.2 Пагинация и фильтры

Списки принимают `limit` (по умолчанию 25, максимум 200) и `offset`. Ответ:

```json
{"items": [...], "total": 137, "limit": 25, "offset": 50}
```

Сортировка — параметром `sort` с полем и направлением (`sort=-created_at`).
Допустимые поля перечисляются в описании каждого эндпоинта, остальные — `400`.

Все фильтры передаются query-параметрами и комбинируются по «И». Диапазоны дат —
`*_from` / `*_to` включительно, формат `YYYY-MM-DD`.

### 5.3 Конкурентность

У `order`, `shipment`, `receipt_batch`, `stock_balance` есть колонка `version`.
Наружу отдаётся заголовком `ETag`. Изменяющие запросы к этим ресурсам обязаны
передавать `If-Match`; несовпадение — `409` `stale_version`. Без заголовка —
`428 Precondition Required`.

Списание остатка выполняется атомарно в той же транзакции:

```sql
UPDATE stock_balance SET qty = qty - :n, version = version + 1
WHERE item_id = :item AND warehouse_id = :wh AND qty - reserved >= :n
```

Ноль обновлённых строк → `insufficient_stock`, транзакция откатывается целиком.

### 5.4 Идемпотентность

Заголовок `Idempotency-Key` обязателен для: создания заказа, добавления коробки,
регистрации скана, проведения складской операции. Ключ и хеш тела сохраняются;
повтор с тем же ключом возвращает прежний ответ и не создаёт вторую запись.
Тот же ключ с другим телом — `409` `conflict`. Срок хранения ключей — 24 часа.

### 5.5 Аудит

Каждое изменение документа, пользователя, прав, справочника и остатка пишется в
`audit_log`: кто, что, когда, значения до и после. Чтение не аудируется.

### 5.6 Прочее

- Все отметки времени в БД — `timestamptz` в UTC; API отдаёт ISO 8601.
  Форматирование в «дд.мм.гггг чч:мм» — задача клиента.
- Денежных величин в системе нет. Количества — целые, вес — `numeric(10,3)`.
- Ответы не кэшируются, кроме `GET /bootstrap` и `GET /catalog` — там `ETag`.

### 6.2 Заказы

| Метод | Путь | Права |
|---|---|---|
| GET | `/orders` | orders: view |
| POST | `/orders` | orders: edit |
| GET | `/orders/{id}` | orders: view |
| GET | `/orders/{id}/history` | orders: view |
| POST | `/orders/{id}/accept` | orders: edit |
| POST | `/orders/{id}/decline` | orders: edit |
| POST | `/orders/{id}/cancel` | orders: edit |

**GET /orders** — параметры: `direction` (`ours`/`theirs`), `status` (можно
несколько), `warehouse_id`, `responsible_id`, `created_from`, `created_to`,
`q` (номер заказа), `limit`, `offset`, `sort`.

Элемент списка: `id`, `number`, `direction`, `status`, `counterparty_warehouse`
(id + имя), `positions_count`, `responsible` (id + имя), `created_at`,
`shipped_at`, `accepted_at`.

**POST /orders** — тело:

```json
{"warehouse_id": 3, "comment": "срочно",
 "positions": [{"article": "100421", "qty": 500}]}
```

Правила: склад-отправитель обязателен и один на весь заказ; позиции
непустые, количества > 0, артикулы существуют и не архивированы; номер заказа
генерирует сервер (см. 7.5); направление — всегда `ours`; статус — `created`;
ответственный — текущий пользователь. Проверка наличия на складе-отправителе:
если запрошено больше свободного остатка — `409` `insufficient_stock` со списком
проблемных позиций.

**POST /orders/{id}/accept** — доступно для `direction = theirs` в статусе
`created`. Переводит в `processing`, создаёт пустую отгрузку (`shipment`),
резервирует остаток по позициям. Иначе — `409` `invalid_transition`.

**POST /orders/{id}/decline** — тело `{"reason": "…"}` (необязательно). Только
`theirs` в статусе `created` → `declined`. Резерв не создавался, снимать нечего.

**POST /orders/{id}/cancel** — тело `{"reason": "…"}`. Только `ours` в статусах
`created` или `processing` → `cancelled`. Если резерв был — снимается.

### 6.3 Отгрузка

| Метод | Путь | Права |
|---|---|---|
| GET | `/shipments` | shipping: view |
| GET | `/shipments/{order_id}` | shipping: view |
| POST | `/shipments/{order_id}/boxes` | shipping: edit |
| DELETE | `/shipments/{order_id}/boxes/{barcode}` | shipping: edit |
| POST | `/shipments/{order_id}/boxes/{barcode}/print` | shipping: edit |
| GET | `/shipments/{order_id}/label/{barcode}` | shipping: view |
| POST | `/shipments/{order_id}/ship` | shipping: edit |

**GET /shipments** — параметры: `status` (`waiting`/`progress`/`done`),
`weight_min`, `weight_max`, `created_from`, `created_to`, `ship_from`, `ship_to`,
`q`, `limit`, `offset`.

Статус вычисляется: коробок нет — `waiting`; есть — `progress`; заказ отгружен —
`done`. Элемент списка содержит `progress` (сколько позиций упаковано полностью
из общего числа), `total_weight`, `responsible`, `created_at`, `shipped_at`.

**POST /shipments/{order_id}/boxes** — тело:

```json
{"article": "100421", "qty": 500, "weight": 10.24}
```

Сервер выдаёт штрихкод (7.6), создаёт коробку, возвращает её вместе с готовым
ZPL для печати. Правила: заказ в статусе `processing`; артикул есть в позициях
заказа; сумма упакованного по позиции не превышает заказанное; вес > 0.

**DELETE …/boxes/{barcode}** — только пока заказ не отгружен.

**POST …/boxes/{barcode}/print** — перепечать: новую коробку не создаёт, пишет
запись в `print_job` с `is_reprint = true`, возвращает ZPL.

**GET …/label/{barcode}** — параметр `format` (`zpl` по умолчанию, `pdf` для
предпросмотра).

**POST /shipments/{order_id}/ship** — тело `{"allow_shortage": false}`. Если
упаковано не всё и `allow_shortage` не выставлен — `409` `conflict` со списком
недостающих позиций. При успехе одной транзакцией: статус заказа → `shipped`,
`shipment.shipped_at`, списание остатка со склада-отправителя, снятие резерва,
записи в `stock_movement` типа `shipment`, событие в истории заказа.

### 6.4 Приёмка

| Метод | Путь | Права |
|---|---|---|
| GET | `/receipts` | receiving: view |
| POST | `/receipts` | receiving: edit |
| GET | `/receipts/{id}` | receiving: view |
| POST | `/receipts/{id}/scans` | receiving: edit |
| DELETE | `/receipts/{id}/scans/{barcode}` | receiving: edit |
| POST | `/receipts/{id}/complete` | receiving: edit |

Партии бывают двух видов: **от поставщика** (создаются через `POST /receipts`
или импортом) и **наши заказы в пути** (создаются автоматически, когда заказ
`ours` переходит в `processing`; поле `order_id` заполнено).

**GET /receipts** — набор фильтров тот же, что у отгрузки. Статус: сканов нет —
`waiting`; есть — `progress`; завершена — `done`.

**GET /receipts/{id}** — возвращает состав партии, полный список ожидаемых
коробок с их штрихкодами и ожидаемым весом, а также отсканированные с
фактическим весом и расхождением.

**POST /receipts/{id}/scans** — тело:

```json
{"barcode": "WH1281187100421", "actual_weight": 22.2}
```

Правила: штрихкод принадлежит этой партии (иначе `barcode_not_found`); ещё не
отсканирован (повтор с тем же `Idempotency-Key` возвращает прежний результат,
без ключа — `409` `barcode_duplicate`); партия не завершена. Сервер считает
расхождение в кг и процентах и сохраняет их.

**DELETE …/scans/{barcode}** — отмена ошибочного скана, коробка возвращается в
ожидаемые. Запрещено после завершения партии.

**POST /receipts/{id}/complete** — тело `{"allow_missing": false}`. Если
отсканировано не всё и флаг не выставлен — `409` со списком недостающих коробок.
При успехе одной транзакцией: неотсканированные коробки помечаются
`is_missing`; партия → `done`; приход на склад по фактически принятым коробкам
(`stock_movement` типа `receipt`); если партия связана с заказом — заказ →
`received`, событие в истории.

|---|---|---|

**GET /stock** — `q`, `warehouse_id`, `below_min`, `limit`, `offset`. Возвращает

`insufficient_stock`. Операция создаёт движение и обновляет баланс в одной
транзакции.

## 7. Бизнес-правила

### 7.1 Направление заказа

`ours` — наш заказ другому складу (мы получатели). `theirs` — чужой заказ нам
(мы отправители). Направление определяется относительно склада текущего
пользователя и задаётся при создании.

### 7.2 Статусы заказа

```
                 accept (theirs)        ship              complete
created ─────────────▶ processing ─────────▶ shipped ─────────▶ received
   │                        │
   │ decline (theirs)       │ cancel (ours)
   ▼                        ▼
declined                cancelled
```

Любой переход, не показанный на схеме, — `409` `invalid_transition`. Каждый
переход пишет запись в `order_status_event` с автором и, если есть, причиной.
Отменённый и отклонённый заказ дальше не двигается.

### 7.3 Резервы

Резерв возникает при `accept` (по позициям заказа на складе-отправителе) и
снимается при отгрузке (переходит в списание) либо при отмене. Свободный
остаток `free = qty − reserved` — именно он проверяется при создании заказа и
ручном списании.

### 7.4 Движения склада

Любое изменение количества создаёт запись в `stock_movement`. Баланс без
движения менять запрещено — это инвариант, проверяемый тестом сверки: сумма
движений по паре «позиция + склад» равна текущему балансу.

Типы движений: `receipt`, `shipment`, `writeoff`, `recount`, `reserve`,
`unreserve`.

### 7.5 Нумерация заказов

Номер выдаёт сервер из последовательности, раздельно по направлениям: `ours` —
с 2001, `theirs` — с 3001. Номер уникален и не переиспользуется.

### 7.6 Штрихкоды коробок

Выдаёт сервер, клиент их не придумывает — иначе при двух рабочих местах коробки
получат одинаковые коды.

```
отгрузка: SH{номер заказа}{артикул}-{порядковый:02d}   SH3029201204-01
приёмка:  WH{код склада}{номер партии}{артикул}[-{порядковый:02d}]
```

Только латиница и цифры: сканеры в режиме клавиатуры не передают кириллицу.
Штрихкод уникален в пределах системы.

### 7.7 Печать этикеток

Приложение получает от сервера готовый ZPL и передаёт его службе устройств.
Порядок жёсткий: **сначала коробка создаётся в базе, потом печатается этикетка**.
Обратный порядок теряет данные при зажёванной ленте. Перепечать не создаёт
вторую коробку.

## 8. Нефункциональные требования

- **Объём.** 20 пользователей, до 5 одновременно, порядка 10 000 заказов и
  100 000 движений в год. Нагрузка ничтожная, но запросы к спискам обязаны
  использовать индексы — при 100 000 строк последовательный скан заметен.
- **Отклик.** 95-й процентиль списков — до 300 мс, карточек — до 150 мс.
- **Логи.** structlog в JSON, сквозной `request-id` из заголовка или
  сгенерированный, во всех записях. Тело запросов не логируется, пароли и
  токены не логируются никогда.
- **Метрики.** Prometheus: количество и длительность запросов по эндпоинтам,
  ошибки по кодам, размер пула соединений.
- **Ошибки.** Sentry на необработанные исключения.
- **Часовой пояс.** Сервер работает в UTC независимо от настроек машины.

## 9. Тестирование

Обязательное покрытие:

**Модульные** — переходы статусов заказа (включая все запрещённые), расчёт
свободного остатка, генерация номеров и штрихкодов, разбор фильтров, проверка
прав по матрице.

**Интеграционные, на реальной БД в контейнере** — каждый эндпоинт: успех, отказ
по правам, отказ по валидации, отказ по состоянию.

**Сценарные, сквозные:**

1. Создание заказа → приём → упаковка коробок → отгрузка → приёмка на стороне
   получателя → сверка остатков на обоих складах.
2. Отгрузка с недостачей: часть позиций не упакована, `allow_shortage`.
3. Приёмка с недостачей: часть коробок не отсканирована, `allow_missing`.
4. Отмена заказа после резервирования — резерв снят, остаток вернулся.
5. Ручная корректировка остатка и сверка журнала движений с балансом.

**Конкурентность** — два параллельных запроса на отгрузку одного заказа: один
успех, второй `409`. Два списания последней единицы товара: одно успех, второе
`insufficient_stock`.

**Идемпотентность** — повтор создания заказа, коробки и скана с тем же ключом не
создаёт дублей.

Порог покрытия сервисного слоя — 80%.

## 10. Конфигурация и развёртывание

Все параметры — переменные окружения, читаются `pydantic-settings`:

```
DATABASE_URL=postgresql+psycopg://prozapas:***@db:5432/prozapas
JWT_SECRET=***
ACCESS_TTL_MIN=15
REFRESH_TTL_DAYS=30
LOG_LEVEL=info
SENTRY_DSN=
WAREHOUSE_CODE=128
```

Docker Compose из трёх контейнеров: `api`, `db`, `nginx`. Тот же compose-файл
используется для разработки. Миграции применяются отдельным шагом до старта
нового контейнера, не в момент импорта приложения.

Сервер разворачивается на машине внутри склада. Наружу выставляется только через
VPN. Бэкап — `pg_dump` по расписанию плюс копия на отдельный носитель.

## 11. Этапы

1. **Каркас и контракт.** Проект, настройки, БД, первая миграция, сид, `/health`,
   `/version`, OpenAPI. Аутентификация и права.
2. **Справочники и остатки.** Каталог, склады, поставщики, остатки, движения,
   ручные операции.
3. **Заказы.** Список с фильтрами, создание, карточка, переходы статусов,
   резервы, история.
4. **Отгрузка и приёмка.** Коробки, штрихкоды, этикетки, списание и приход,
   сценарии с недостачей.
5. **Главная, поиск по штрихкоду, журналы печати и аудита.**
6. **Обвязка.** Метрики, Sentry, бэкапы, CI, деплой.

После этапа 3 приложение уже можно переключать на сервер по основным экранам.

## 13. Критерии приёмки

- [ ] Все эндпоинты раздела 6 реализованы и описаны в OpenAPI.
- [ ] Матрица прав из раздела 4 соблюдается, проверена тестами на каждой роли.
- [ ] Пять сквозных сценариев из раздела 9 проходят на чистой базе.
- [ ] Сумма движений по каждой паре «позиция + склад» равна балансу.
- [ ] Параллельная отгрузка одного заказа даёт ровно одну успешную операцию.
- [ ] Повтор любого изменяющего запроса с тем же `Idempotency-Key` не создаёт
      дубль.
- [ ] Миграции накатываются на пустую базу и на базу с данными.
- [ ] Приложение работает со всеми экранами через API без обращения к JSON-файлу.
