# API ProЗапас — контракт

HTTP-интерфейс между десктопным приложением и сервером.

Документ описывает актуальный контракт после пересмотра модели данных. Он
заменяет [backend-spec_old.md](backend-spec_old.md) — расхождения перечислены в
разделе 9. Смежные документы:
[database-architecture.md](database-architecture.md) — таблицы и границы
сервисов, [architecture.md](architecture.md) — общая картина.

---

## 1. Границы

**Входит:** аутентификация, права, справочники, остатки, заказы, отгрузка,
приёмка, пользователи, сводка для главной.

**Не входит:** работа с оборудованием (сканер, весы, принтер — это служба
устройств на рабочем месте, см. [devices-service.md](devices-service.md)),
макеты этикеток (собирает клиент), обмен с 1С (решение отложено).

## 2. Общие правила

| | |
|---|---|
| Префикс | `/api/v1` |
| Формат | JSON, UTF-8 |
| Время | ISO 8601 в UTC, `2026-07-22T09:00:00Z` |
| Числа количеств | дробные, до трёх знаков — в справочнике есть метры и листы |
| Ошибки | RFC 9457, `application/problem+json` |

### 2.1 Списки

Все списочные ответы одинаковы:

```json
{"items": [...], "total": 128, "limit": 50, "offset": 0}
```

`limit` по умолчанию 50, максимум 200. Сортировка — параметр `sort`, по
умолчанию у документов «новые сверху».

### 2.2 Ошибки

```json
{
  "type": "https://prozapas/errors/insufficient-stock",
  "title": "Недостаточно свободного остатка",
  "status": 409,
  "positions": [{"article": "100421", "requested": 500, "available": 320}]
}
```

Клиент ветвится по `type`, показывает `title`, машиночитаемые детали разбирает
из дополнительных полей.

| Код | Когда |
|---|---|
| `400` | тело или параметры не разобрались |
| `401` | нет токена, истёк, отозван |
| `403` | нет прав на раздел или запрещено правилом |
| `404` | объекта нет или он удалён |
| `409` | конфликт версий, недопустимый переход статуса, нехватка остатка |
| `422` | нарушено доменное правило: отрицательное количество, архивный товар |
| `428` | изменение без `If-Match` |
| `503` | база недоступна |

### 2.3 Конкурентность

У документов с колонкой `version` — `sales_order`, `shipment`, `stock_balance`,
`receipt_batch` — ответ несёт `ETag`, а изменение требует `If-Match`:

```
GET /api/v1/orders/60          → 200, ETag: "7"
POST /api/v1/orders/60/accept  ← If-Match: "7"
                               → 409, если версия уже 8
```

Без заголовка — `428`. Это то, что не даёт двум кладовщикам отгрузить один заказ
дважды.

### 2.4 Идемпотентность

Заголовок `Idempotency-Key` обязателен только на `POST /orders`: у заказа нет
естественного ключа, а повтор из-за таймаута создал бы дубль.

Скану и коробке ключ не нужен — их защищают уникальные ограничения
`UNIQUE (batch_id, barcode)` и `shipment_box.barcode`. Повторный запрос
возвращает существующий объект с `200`, а не ошибку.

## 3. Аутентификация

Короткий access-JWT плюс refresh в базе.

```
POST /api/v1/auth/login     {login, password}  → {access, refresh, user, permissions}
POST /api/v1/auth/refresh   {refresh}          → {access, refresh}
POST /api/v1/auth/logout    {refresh}          → 204
GET  /api/v1/auth/me                           → {user, permissions}
```

**Access** — JWT на 15 минут, на сервере не хранится. Содержит всё для проверки
прав без обращения к базе:

```json
{
  "sub": "12", "login": "i.kuznetsov", "name": "Кузнецов И.А.",
  "role": "admin", "warehouse_id": 4,
  "perms": {"orders": "edit", "shipping": "edit", "receiving": "edit",
            "catalog": "edit", "stock": "edit", "users": "edit"},
  "iat": 1785312000, "exp": 1785312900, "jti": "…"
}
```

**Refresh** — не JWT, а 32 случайных байта. В базе лежит только хеш, поэтому
утечка дампа входа не даёт. Срок 30 дней.

**Ротация.** При каждом обновлении старый refresh отзывается, выдаётся новый.
Если предъявлен уже отозванный — это признак кражи, отзывается **вся цепочка**
пользователя.

Вход — по полю `login`. Это отдельная колонка `user_account.login`, а не часть
адреса почты: форма заведения сотрудника спрашивает логин явно и лишь предлагает
часть адреса как значение по умолчанию.

При успешном входе обновляется `last_login_at`. Пароли — argon2id.

| Ситуация | Ответ |
|---|---|
| Неверный логин или пароль | `401 invalid_credentials`, без уточнения, что именно |
| Пользователь заблокирован | `403 user_blocked` |
| Access истёк | `401 token_expired` — клиент обновляет и повторяет молча |
| Refresh истёк или отозван | `401 invalid_token` — экран входа |
| Пять неудач подряд с адреса | задержка 30 секунд |

Различать «нет такого логина» и «неверный пароль» нельзя — это перебор учётных
записей.

## 4. Права

Матрица «роль × раздел», два уровня доступа. Разделы: `orders`, `shipping`,
`receiving`, `catalog`, `stock`, `users`.

| Раздел | manager | stockman | admin |
|---|---|---|---|
| orders | просмотр + изменение | просмотр | просмотр + изменение |
| shipping | просмотр | просмотр + изменение | просмотр + изменение |
| receiving | просмотр | просмотр + изменение | просмотр + изменение |
| catalog | просмотр + изменение | просмотр | просмотр + изменение |
| stock | просмотр | просмотр + изменение | просмотр + изменение |
| users | нет доступа | нет доступа | просмотр + изменение |

Матрица едет в access-токене, поэтому проверка — чистая функция без запроса в
базу. Максимальная задержка применения новых прав — **15 минут**, срок жизни
токена. Мгновенная отмена доступа делается блокировкой: она бьёт по refresh
сразу.

### 4.1 Где проверяется

Грубая проверка «раздел + уровень» — декларативно на маршруте:

```python
@router.post("/orders/{id}/accept",
             dependencies=[Depends(requires(Section.ORDERS, Access.EDIT))])
```

Правила, которым нужен сам объект, — в сервисном слое:

- нельзя заблокировать или удалить себя;
- нельзя изменить собственную роль;
- последний активный администратор не блокируется и не удаляется;
- матрицу прав правит только `admin`.

Разделение: что проверяется до загрузки данных — на маршруте, что требует данных
— в сервисе.

## 5. Эндпоинты

Права указаны как «раздел: уровень».

### 5.1 Служебные

| Метод | Путь | Права | Назначение |
|---|---|---|---|
| GET | `/health` | — | живость, делает `SELECT 1` |
| GET | `/version` | — | версия сборки и ревизия схемы |
| GET | `/bootstrap` | вход | справочники одним запросом |
| GET | `/dashboard` | вход | сводка для главной |
| GET | `/barcodes/resolve` | вход | чем является отсканированный код |

**`GET /bootstrap`** — склады, роли, разделы, права, текущий пользователь,
версия каталога. Один поход вместо шести при старте приложения.

**`GET /barcodes/resolve?code=…`** — возвращает тип и идентификатор: коробка
приёмки, коробка отгрузки, артикул или номер заказа. Без него клиенту пришлось
бы угадывать, какой экран открыть по скану.

**`GET /dashboard`** — три счётчика (заказы в работе с разбивкой, к отгрузке, к
приёмке), задачи текущего пользователя по его роли (до 8) и последние события
из истории заказов (до 6).

### 5.2 Заказы

| Метод | Путь | Права |
|---|---|---|
| GET | `/orders` | orders: view |
| POST | `/orders` | orders: edit |
| GET | `/orders/{id}` | orders: view |
| GET | `/orders/{id}/history` | orders: view |
| POST | `/orders/{id}/accept` | orders: edit |
| POST | `/orders/{id}/decline` | orders: edit |
| POST | `/orders/{id}/cancel` | orders: edit |

**`GET /orders`** — параметры: `direction` (`ours`/`theirs`, обязателен — это
вкладка), `status` (можно несколько), `warehouse_id`, `responsible_id`,
`created_from`, `created_to`, `q` (префикс номера), `limit`, `offset`, `sort`.

Элемент списка соответствует колонкам экрана:

```json
{"id": 60, "number": "3026", "direction": "theirs", "status": "processing",
 "counterparty_warehouse": {"id": 1, "name": "Склад №1"},
 "positions_count": 4,
 "responsible": {"id": 12, "name": "Кузнецов И.А."},
 "created_at": "2026-07-21T09:00:00Z",
 "shipped_at": null, "accepted_at": null}
```

**`POST /orders`** — требует `Idempotency-Key`.

```json
{"warehouse_id": 3, "comment": "срочно",
 "positions": [{"article": "100421", "qty": 500}]}
```

Правила: склад-контрагент один на заказ; позиции непустые, количества больше
нуля; артикулы существуют и не архивированы; номер выдаёт сервер; направление
всегда `ours`; статус `created`; ответственный — текущий пользователь.

Запрошено больше свободного остатка → `409 insufficient_stock` со списком
проблемных позиций.

**`POST /orders/{id}/accept`** — только `theirs` в статусе `created`. Одной
транзакцией: переводит в `processing`, создаёт пустую отгрузку, резервирует
остаток. Иначе `409 invalid_transition`.

**`POST /orders/{id}/decline`** — тело `{"reason": "…"}`, необязательно. Только
`theirs` в `created` → `declined`. Резерва не было, снимать нечего.

**`POST /orders/{id}/cancel`** — тело `{"reason": "…"}`. Только `ours` в
`created` или `processing` → `cancelled`. Резерв, если был, снимается.

### 5.3 Отгрузка

| Метод | Путь | Права |
|---|---|---|
| GET | `/shipments` | shipping: view |
| GET | `/shipments/{order_id}` | shipping: view |
| POST | `/shipments/{order_id}/boxes` | shipping: edit |
| DELETE | `/shipments/{order_id}/boxes/{box_id}` | shipping: edit |
| POST | `/shipments/{order_id}/boxes/{box_id}/printed` | shipping: edit |
| POST | `/shipments/{order_id}/ship` | shipping: edit |

**`GET /shipments/{order_id}`** — карточка с прогрессом: позиции заказа,
сколько по каждой упаковано, список коробок, общий вес, ответственный.

**`POST …/boxes`** — тело `{"article": "100421", "qty": 200, "weight": 4.2}`.
Ответ содержит `barcode`, **выданный сервером**: при двух рабочих местах
клиенты выдали бы одинаковые коды.

Коробка создаётся **до печати**. Зажевало ленту — коробка на месте, этикетка
перепечатывается; обратный порядок теряет данные. Поэтому создание и отметка о
печати — две разные операции.

Упаковано больше заказанного → `422`.

**`POST …/boxes/{box_id}/printed`** → `204`. Проставляет `printed_at`.
Перепечать вызывает его повторно и второй коробки не создаёт.

**`POST …/ship`** — требует `If-Match`. Одной транзакцией: списывает остаток,
переводит заказ в `shipped`, закрывает отгрузку. Не все позиции собраны →
`409 incomplete_shipment`.

### 5.4 Приёмка

| Метод | Путь | Права |
|---|---|---|
| GET | `/receipts` | receiving: view |
| GET | `/receipts/{id}` | receiving: view |
| POST | `/receipts/{id}/scans` | receiving: edit |
| DELETE | `/receipts/{id}/scans/{barcode}` | receiving: edit |
| POST | `/receipts/{id}/complete` | receiving: edit |

**`GET /receipts/{id}`** — партия с прогрессом: позиции, ожидаемое число коробок
и вес, сколько уже отсканировано, расхождения.

Пока партия в работе, прогресс считается по строкам `receipt_scan`. После
завершения — по агрегату в позициях партии. Один источник правды в каждый
момент.

**`POST …/scans`** — тело `{"barcode": "…", "article": "100421",
"actual_weight": 22.1}`.

Идемпотентен: повторный скан того же штрихкода упирается в
`UNIQUE (batch_id, barcode)` и возвращает существующую строку с `200`. Расхождение
веса считает сервер, клиент присылает только факт.

**`DELETE …/scans/{barcode}`** → `204`. Отмена ошибочного скана.

**`POST …/complete`** — требует `If-Match`. Самая насыщенная транзакция в
системе: свернуть сканы в агрегат по позициям, оприходовать остатки, закрыть
партию, перевести связанный заказ в `received`, удалить строки сканов, записать
полный список сканов в `audit_log`. Всё или ничего.

Партия не в статусе `progress` → `409`.

### 5.5 Остатки

| Метод | Путь | Права |
|---|---|---|
| GET | `/stock` | stock: view |
| GET | `/stock/summary` | stock: view |
| GET | `/stock/{item_id}` | stock: view |
| GET | `/stock/{item_id}/movements` | stock: view |
| POST | `/stock/operations` | stock: edit |

**`GET /stock`** — параметры `q` (артикул или наименование), `warehouse_id`,
`below_min`, `limit`, `offset`. Элемент: артикул, код 1С, наименование,
единица, `qty`, `free` (= `qty − reserved`), `reserved`.

**`POST /stock/operations`** — ручная операция из карточки товара:

```json
{"article": "100512", "warehouse_id": 1, "type": "writeoff",
 "qty": 12.5, "comment": "брак при разгрузке"}
```

Типы: `receipt`, `shipment`, `writeoff`, `recount`. Для `recount` `qty` — не
дельта, а новое значение остатка.

У списания и корректировки **нет документа**: `doc_type` и `doc_id` остаются
пустыми, в истории показывается `comment`. Нумерованных актов списания система
не ведёт.

Списание больше свободного остатка → `422`.

### 5.6 Справочник, склады, поставщики

| Метод | Путь | Права |
|---|---|---|
| GET | `/catalog` | catalog: view |
| POST | `/catalog` | catalog: edit |
| GET | `/catalog/{id}` | catalog: view |
| PATCH | `/catalog/{id}` | catalog: edit |
| POST | `/catalog/{id}/archive` | catalog: edit |
| GET | `/warehouses` | вход |
| POST | `/warehouses` | users: edit |
| PATCH | `/warehouses/{id}` | users: edit |
| GET | `/suppliers` | receiving: view |
| POST | `/suppliers` | receiving: edit |

**`GET /catalog?q=…`** — поиск по наименованию, артикулу и коду 1С через GIN по
`tsvector`-колонке. Позиция с движениями не удаляется, а архивируется.

### 5.7 Пользователи и права

| Метод | Путь | Права |
|---|---|---|
| GET | `/users` | users: view |
| POST | `/users` | users: edit |
| GET | `/users/{id}` | users: view |
| PATCH | `/users/{id}` | users: edit |
| POST | `/users/{id}/block` | users: edit |
| POST | `/users/{id}/unblock` | users: edit |
| POST | `/users/{id}/password` | users: edit |
| DELETE | `/users/{id}` | users: edit |
| GET | `/roles` | вход |
| GET | `/permissions` | users: view |

**`POST /users`** — тело содержит `login` отдельным полем. Логин и почта
уникальны среди неудалённых. Пароль по умолчанию выдаётся сотруднику при
заведении и меняется при первом входе.

**`DELETE /users/{id}`** — мягкое удаление, проставляет `deleted_at`.

## 6. Бизнес-правила

### 6.1 Статусы заказа

```
created ──▶ processing ──▶ shipped ──▶ received
   │             │
   ▼             ▼
declined     cancelled
```

`accept` доступен только для `theirs` в `created`; `decline` — там же; `cancel`
— для `ours` в `created` или `processing`. Всё остальное → `409
invalid_transition`.

### 6.2 Резервы

Резерв создаётся при `accept`, снимается при `cancel` и превращается в списание
при отгрузке. Движения типа `reserve` и `unreserve` не меняют `qty`, поэтому
исключаются из сверки «сумма движений = баланс».

### 6.3 Движения склада

Любое изменение остатка проходит через единственную точку — `inventory.apply()`,
которая в одной операции пишет движение и обновляет баланс. Никакой другой код
не трогает `qty` напрямую. Только так журнал не расходится с балансом.

### 6.4 Нумерация

Номера заказов выдаёт сервер из последовательностей: исходящие с 2001,
входящие с 3001. Клиент номер не предлагает.

Штрихкоды коробок выдаёт сервер при создании коробки.

## 7. Стык с базой

Синхронный SQLAlchemy, обычные `def`-эндпоинты — FastAPI уводит их в пул
потоков. Асинхронный ORM окупается при сотнях одновременных запросов, здесь их
десятки.

Пул на 10 соединений с `pool_pre_ping`, сессия живёт ровно один запрос.
Подробности — [database-architecture.md §3.7](database-architecture.md).

Транзакцию открывает только тот сервис, которого позвал API; слой API
транзакций не открывает и бизнес-правил не содержит.

## 8. Сборка ответов

Слой API — единственное место, которому позволено знать про несколько доменов
сразу. Списки, где нужны чужие данные, собираются **пакетными** вызовами:

```python
rows, total = orders.list_orders(session, f, user, limit=limit, offset=offset)
warehouses = catalog.get_warehouses(session, {o.counterparty_warehouse_id for o, _ in rows})
users = accounts.get_users(session, {o.responsible_user_id for o, _ in rows if o.responsible_user_id})
```

Три запроса на страницу, а не три на строку. `JOIN` через границу сервиса
запрещён — он стирает границу.

## 10. Критерии приёмки

- [ ] OpenAPI генерируется и из неё собирается типизированный клиент для
      десктопа.
- [ ] Вход, обновление и выход работают; отозванный refresh обрушивает всю
      цепочку.
- [ ] Матрица прав применяется: `stockman` не открывает `/users`, `manager` не
      правит остатки.
- [ ] Изменение документа без `If-Match` даёт `428`, с устаревшим — `409`.
